# Privacy and Data-Residency Policy

This document defines the operational privacy posture for the Kant relay and the responsibilities of operators deploying it. It is written to support release readiness and security review without overstating legal compliance.

## 1. Data processing model

Kant is designed around a relay-assisted peer-to-peer architecture. The relay is not a message store and does not process plaintext user messages. The relay is intended to process:

- public registry metadata needed for peer discovery
- connection and reservation metadata required for NAT traversal
- health, readiness, and metrics data for operational monitoring
- certificate and TLS data for public HTTPS termination

The relay does not intentionally store:

- message content
- message history
- contact lists
- user identity keys beyond the relay's own long-term identity seed
- private user payloads in the relay process

Client data remains on the user's device unless a separate deployment chooses to retain operational telemetry or backups outside the relay itself.

## 2. What the relay can observe

A relay operator can observe operational metadata necessary for service delivery, including:

- relay uptime and health
- peer connection and reservation events
- peer lookup and registration traffic
- public IP and DNS information of the relay service
- request and response timing for operational metrics

Depending on deployment, the operator may also observe:

- logs generated by Caddy, Docker, or the relay itself
- Prometheus metrics and alert data
- DNS and certificate lifecycle events

## 3. What the relay does not observe

The relay does not intentionally process or store:

- plaintext messages exchanged between peers
- precise message metadata beyond route and connection metadata needed for relay operation
- full contact graphs or user message history at the server layer

This is an architectural property of the protocol and should be documented in any operator-facing deployment guide.

## 4. Data categories and retention

### Relay operational logs
Logs are operational only and should be retained only as long as necessary for troubleshooting and security review.

Recommended retention guidance:
- application logs: 30 to 90 days, unless a stricter policy is required
- security logs: retain longer if needed for incident investigation
- access logs for Caddy or reverse-proxy services: 7 to 30 days unless a longer retention is required by local policy

### Metrics and dashboards
Metrics should be retained according to the monitoring policy, with a default operational retention window of 14 to 90 days depending on the monitoring stack.

### Relay state
The relay's state is intentionally ephemeral and not designed to hold user message content. The only long-lived identity file is the relay seed, which must be protected and backed up securely.

### Backups
The relay seed backup and any TLS material backups should be encrypted at rest and restricted to the operational team. Retention should match the deployment's operational continuity requirements and should not exceed what is necessary for recovery.

## 5. Data residency and deployment choices

Kant supports both self-hosted and operator-controlled deployments. The following should be considered in any deployment decision:

- the relay may be hosted in a jurisdiction chosen by the operator
- client device data remains outside the relay unless a user or org explicitly stores data elsewhere
- any external monitoring, log shipping, or backup service used by the operator is governed by that operator's residency and retention policy

A deployer should document the following before production exposure:

- where the relay is hosted
- where logs and metrics are stored
- whether backups are exported to a third-party system
- what the retention period is for telemetry and backups
- whether the deployment exposes any operation logs to a managed provider

## 6. Minimization principles

Operators should minimize data collection to the extent practical:

- avoid collecting unnecessary user payload data
- retain logs only for the time required for operations and incident response
- avoid logging plaintext message content, user keys, or contact data
- restrict access to operational dashboards and backups to authorized administrators only

## 7. Security vulnerability disclosure

The project should define a clear disclosure path for security researchers and operators.

Recommended policy:
- report suspected vulnerabilities to the project maintainer or designated security contact
- provide enough detail for the issue to be understood and reproduced
- coordinate disclosure timing with the security team and release owners
- avoid public disclosure until a fix or mitigation is available or a reasonable disclosure window has been agreed

The specific contact channel should be documented in the project release documentation and maintained by the operator of the published service.

## 8. Privacy controls for operators

Operators should implement the following controls:

- restrict access to monitoring dashboards and relay hosts
- use TLS encryption for all public-facing relay endpoints
- keep service logs free of plaintext payloads
- encrypt backups and seed material at rest
- rotate keys and credentials on a schedule or after a suspected compromise
- ensure production monitoring excludes personal message content

## 9. Compliance posture

This document provides a practical privacy baseline for the project and its deployment model. It is not a legal opinion or formal compliance certification. Operators remain responsible for:

- their own jurisdictional requirements
- any contractual obligations related to service hosting or data processing
- user-facing privacy disclosures in the environment where the product is deployed

## 10. Release gate

A production release should not proceed without:

- a documented deployment-specific data processing notice
- a retention policy for logs, metrics, and backups
- a clear operator statement of data residency and third-party processors
- a recorded vulnerability disclosure path
- confirmation that no operational telemetry stores plaintext message content
